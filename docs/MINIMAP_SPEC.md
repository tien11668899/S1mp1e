# 玻璃小地圖 — 設計規格（26.3 為參考實作）

狀態：**26.3 已實作並通過遊戲內驗收**（見文末「驗收結果」）；FPS 開／關對照基準尚未執行。其他版本尚未移植。標 **待驗證** 的項目是還沒實測過的假設。

程式位置（`versions/mc263`）：`client/minimap/MinimapData.java`（資料層）、`MinimapColors.java`（每格顏色）、`MinimapHud.java`（繪製）、`MinimapRenderState.java`；`client/module/MinimapModule.java`（設定）；`mixin/MinimapChunkMixin.java`、`MinimapBlockMixin.java`（掛點）；著色器 `assets/liquidglass/shaders/core/minimap.fsh`（管線在 `GlassPipeline`）；驗收工具 `DevShot` 的 `minimap` 模式、`Bench` 的 `S1MP1E_BENCH_MINIMAP`。

## 目標

- 畫面角落一個圓形小地圖，外框是和全 UI 一樣的液態玻璃（同一種材質、同一個圓角規則）。
- **不影響 FPS**：開著小地圖跑 `Bench` 的三個場景，平均 FPS 在量測雜訊內、1 % / 0.1 % low 不退步、超過 20 ms 的幀數不增加（驗收方式見「效能驗收」）。
- 符合 `Module.java` 的原則：只畫畫面，不替玩家做任何動作、不送也不改封包。

## 實體顯示：只在「自己開的世界」

雷達類資訊（看得到牆後的人和怪）是伺服器最常禁止的，所以只在**自己當主機的世界**開放：單人世界，或自己開成區網的世界。判斷用 `Minecraft.hasSingleplayerServer()`（客戶端自己跑著內建伺服器）；以區網訪客身分加入別人的世界、或連到任何伺服器時一律不顯示。

| 顯示什麼 | 什麼時候 | 樣式 |
|---|---|---|
| 其他玩家 | 自己的世界裡一直顯示 | 同心兩層圓：外面一顆較大的液態玻璃圓，裡面一顆較小的彩色實心圓，彩色圓畫在玻璃之上（見下） |
| 生物、掉落物 | 自己的世界裡，**按住 Tab（原版「玩家列表」鍵，跟著玩家的改鍵走）**時顯示，放開淡出 | 敵對生物紅點、其他生物黃點、掉落物小白點（扁平，不做玻璃，數量可能很多） |

效能：只在要顯示時才走訪實體，而且只取地圖半徑內的；上限 256 個點，超過就只畫最近的。所有點組成一批四邊形一次畫完。

**垂直範圍**（實作驗收時加入）：高度差 8 格以內正常顯示；8–24 格畫得小一點、淡一點（和其他玩家的高度提示一致）；超過 24 格不顯示。原因是驗收時實測，站在地表按 Tab 會看到幾十隻洞穴裡的殭屍、骷髏、蝙蝠——即使在自己的世界，那也是雜訊，而且像透視。

### 玩家標記：大玻璃圓 + 裡面的小彩色圓

同心圓，從外到內、也是從下層到上層：

```
     ╭─────────╮
    │   ╭───╮   │   外圈 = 液態玻璃圓：直徑 9 GUI px（地圖直徑 96 時），比較大；畫在下層，透出並折射地圖
    │   │ ● │   │   內圈 = 彩色實心圓：直徑 5 GUI px，比較小、位於玻璃圓正中間；畫在上層（蓋在玻璃之上）
    │   ╰───╯   │
     ╰─────────╯
```

也就是：繪製順序先玻璃、後彩色圓；看起來是一顆玻璃珠裡嵌著一顆彩色圓點，玻璃從彩色圓四周露出一圈。

- **玻璃要折射「地圖」，不是世界**：現有的玻璃（`HudGlass`、`GlassRing`）取樣的是渲染 GUI 前抓下來的**世界畫面**，GUI 自己畫的東西（包括小地圖）不在裡面。若直接用 `HudGlass` 畫玩家標記，玻璃圓裡會透出小地圖後面的世界，像在地圖上開了洞。所以玩家標記的玻璃底圓改由 `minimap.fsh` 自己畫：同一條管線多一種「透鏡」模式，四邊形只蓋住標記範圍，在圓內對**地圖貼圖**做折射偏移 + 霜化模糊 + 頂部高光 + 邊緣亮線，參數照 `glass.fsh` 的材質（IOR 1.4、frost 0.5），看起來和其他玻璃是同一種材質，折射的卻是地圖本身。
- **顏色**：從玩家 UUID 雜湊挑一個 Apple 系統色（藍 `#0A84FF`、綠 `#30D158`、橘 `#FF9F0A`、粉 `#FF375F`、紫 `#BF5AF2`、青 `#64D2FF`、黃 `#FFD60A`、靛 `#5E5CE6`），同一個玩家每次都同色。
- **高度差**：對方比你高或低超過 8 格時，彩色圓縮小一點並降低不透明度，一眼看得出不在同一層。
- **超出地圖範圍**：整顆標記貼在玻璃外框內緣，沿著方向移動；縮成 0.8 倍表示「在範圍外」。
- **名字**：預設不顯示；可開「顯示玩家名稱」，在標記下方畫小字（用既有的 `HudText`）。
- **自己**：同樣的玻璃圓 + 內圈，內圈是**白色**，固定在地圖中心；任何世界（包括伺服器）都顯示，因為那只是自己的位置。其他玩家的配色不會用白色，避免混淆。「跟著朝向轉」模式下地圖上方就是自己面向的方向；「北方朝上」模式下用下面的「朝向光束」表示。

### 朝向光束（北方朝上模式）

不用硬邊的三角形，而是像陰影一樣從自己的標記往面向的方向散開、越遠越淡的一道柔光（類似 Apple 地圖的方向光束）：

```
              ░          ← 最外緣：完全透明
            ░░▒░░
           ░▒▒▓▒▒░       ← 越靠近標記越亮
             ╭─╮
             │●│         ← 自己的標記（玻璃圓 + 白色內圈）
             ╰─╯
```

- **形狀**：以標記中心為頂點的扇形，張角約 60°；扇形兩側的邊不是硬線，而是往外逐漸淡掉（角度方向也做平滑衰減）。
- **淡出**：從玻璃圓外緣開始，不透明度約 0.45 → 0，沿距離平滑衰減（`smoothstep`），長度約標記直徑的 3 倍；沒有任何硬邊。
- **顏色**：白色，和自己的內圈同色系。
- **層次**：地圖 → 光束 → 玻璃圓 → 白色內圈。光束畫在玻璃圓下面，所以從玻璃圓邊緣「透出來」往外散。
- **轉動**：用玩家朝向（partial tick 內插），再做和縮放動畫一樣的指數平滑，轉頭時光束柔順地跟著轉，不會抖。自由視角轉鏡頭時不動（跟著角色，不跟鏡頭）。
- **繪製**：`minimap.fsh` 的另一種模式，一個蓋住扇形範圍的小四邊形，角度與距離衰減都在片段著色器裡算；成本是一個小四邊形。
- 「跟著朝向轉」模式下不畫（光束永遠朝上，沒有資訊量）。

玩家標記的成本：每位玩家兩個小四邊形（透鏡 + 彩色圓），全部在同一次繪製裡；自己的世界裡玩家數量很少，可以忽略。

## 不做的事（公平性）

| 不做 | 原因 |
|---|---|
| 在伺服器上（或別人的區網世界）顯示其他玩家、生物、掉落物 | 小地圖最常被伺服器禁止的就是這個（等同雷達）；自己的世界例外，見上 |
| 洞穴／地下模式（以玩家高度切一層） | 會看到牆後的洞穴 = 類透視 |
| 地獄、終界頂部等「有天花板」的維度 | 地表高度圖在地獄是基岩頂，畫出來沒意義；改用切層又變成洞穴模式。這些維度只顯示指北的玻璃外框與「此維度不顯示地圖」 |
| 用伺服器沒送來的資料 | 只畫客戶端已經載入的區塊，也就是玩家本來就看得到的地形 |

判斷「有天花板」用 `DimensionType.hasCeiling()`（26.3 有這個方法）。

## 為什麼不會吃 FPS — 架構重點

很多小地圖模組吃 FPS，是因為**每幀從天空再渲染一次世界**（第二個攝影機、第二個渲染通道）。這裡完全不這樣做，而是跟原版「地圖」物品一樣，把每一格的**地表顏色**算成一張 2D 貼圖：

```
區塊載入／方塊變動 ──► 標記該區塊「髒」──► 每幀限時處理幾個髒區塊（算 16×16 顏色）
                                                     │
                                                     ▼
                                     只上傳那 16×16 一小塊到 GPU（1 KB）
                                                     │
每幀繪製：一個貼圖四邊形 + 一圈玻璃外框 ◄────────────────┘
```

所以每幀固定成本只有「畫一個四邊形 + 一圈玻璃」，跟一個 HUD 膠囊差不多；地圖內容只在**地形真的改變時**才重算，**玩家移動不會觸發任何重算或上傳**。

### 1. 資料：每格一個顏色

- 每個欄位 (x, z)：`chunk.getHeight(Heightmap.Types.WORLD_SURFACE, x, z)` 取地表高度（高度圖查表，O(1)），讀那一格的 `BlockState`，`getMapColor(level, pos)` 取地圖色。
- 明暗：和原版地圖一樣，比較北邊鄰格的高度決定 `MapColor.Brightness`（高 = 亮、低 = 暗），再用 `calculateARGBColor(brightness)` 得到 ARGB。
- 水：往下數水深，用深度決定明暗（原版地圖的做法），淺水看得到底下的顏色感。
- 鄰格依賴：明暗要看北邊鄰格，所以一個區塊載入時，**順便把它南邊鄰區塊的最北一列標髒**（只重算 16 格）。
- 全部在客戶端執行緒做（區塊資料不保證跨執行緒安全，不冒險），用 `BlockPos.MutableBlockPos`、重複使用的陣列，**每幀零配置**（`PERFORMANCE.md` 量過 GC 停頓是卡頓主因之一）。

### 2. 什麼時候重算（髒區塊）

| 事件 | 掛點（26.3） | 動作 |
|---|---|---|
| 區塊從伺服器載入 | `ClientChunkCache.replaceWithPacketData` RETURN | 標髒整個區塊 + 南鄰最北一列 |
| 方塊變動 | `ClientLevel.sendBlockUpdated` | 只有在變動的方塊**高於或等於該欄的「相關高度」**時才標髒（地底挖礦不觸發）。相關高度每格記一個 short：一般方塊是著色用的地表高度，水面則是水底下一格（水深會改變顏色）。標髒的是那一欄和它南邊一欄（§7.1）；同一區塊累積超過 24 欄時，改成重算整個區塊一次（爆炸、大範圍填充）。原本設想的「250 ms 內最多一次」由這兩條取代：單欄重算只有幾微秒，不需要節流 |
| 區塊卸載 | `ClientChunkCache.drop` | **不清除**：保留玩家看過的地形顏色，直到被新資料覆蓋 |
| 換維度／離開世界 | 既有的 tick 掛點 | 清空貼圖與佇列 |

髒區塊佇列依「離玩家距離」排序，近的先算。

### 3. 每幀時間預算

- 每幀最多花 **0.25 ms**（`System.nanoTime()` 量）處理髒區塊，超過就留到下一幀。
- 估計每區塊 256 格 × 約 100–200 ns ≈ 25–50 µs → 每幀可處理 5–10 個區塊。**待驗證**（實作後用統計開關實測）。
- 剛進世界、視距 12 時約 625 個區塊 → 約 1–2 秒填滿，期間地圖從玩家周圍往外「長出來」（未知區域顯示為半透明深色），這也是一個好看的進場效果。

### 4. GPU 貼圖：環狀貼圖，移動零成本

- 一張 `DynamicTexture`，大小取「≥ (2 × 視距 + 1) × 16」的 2 的冪：視距 ≤ 15 用 512×512（1 MB），≤ 31 用 1024×1024（4 MB）。進世界／改視距時決定一次。
- **環狀定址**：世界座標 (x, z) 對應貼圖像素 (x mod N, z mod N)。玩家走多遠都不用搬移貼圖內容，取樣器用 `AddressMode.REPEAT` 讓著色器自然繞回。
- 上傳只上傳變動的 16×16 塊：`CommandEncoder.writeToTexture(GpuTexture, ByteBuffer, …, x, y, w, h)`（26.3 有這個多載；參數順序 **待驗證**）。一個區塊 1 KB。
- 同一幀多個區塊各自上傳小塊即可；不要因為一格變動就上傳整張 1 MB。

### 5. 繪製：一個四邊形 + 一圈玻璃

- **地圖本體**：自訂 `GuiElementRenderState`（照 `RoundRectRenderState` / `GlassRectRenderState` 的做法進 26.x 的延遲 GUI 渲染），輸出一個正方形四邊形：
  - 四個頂點的貼圖座標在 CPU 端依「玩家內插位置（partial tick）、朝向、縮放」算好 → 旋轉、平移、縮放都不需要額外 uniform。
  - 片段著色器 `minimap.fsh`：取樣地圖貼圖；用頂點顏色帶進來的「本地座標」算形狀的距離場（SDF）——圓形用到圓心距離、圓角正方形用圓角矩形 SDF——**形狀外丟棄、邊緣 1 px 抗鋸齒**；alpha 為 0 的未知區塊畫成半透明深色。形狀只是著色器裡的一個分支，兩種形狀成本相同。管線用 `GlassPipeline` 已有的「建立 + 預編譯」流程。
- **玻璃外框**：`GlassRing.glass(…)`（`AttackRing` 已在用的玻璃環）：圓形用形狀 0（圓），正方形用形狀 1（圓角正方形），圓角半徑照 `GlassCorners` 的規則和 hotbar 一致（「圓角都要一樣」）。只有這一圈是玻璃，裡面是不透明地圖，不需要折射 → 背景複製只多一個外框大小的區域（`PERFORMANCE.md`「Liquid glass cost」：玻璃成本幾乎都在背景複製，而現在只複製玻璃元素讀得到的區塊）。
- **自己的標記**：中心一顆玻璃圓 + 白色內圈（和其他玩家同一種標記，見「玩家標記」）。
- **指北**：外框上一個小「N」，隨地圖旋轉沿著外框移動（正方形時沿著圓角正方形的邊走）。
- 每幀不做任何文字排版以外的 CPU 工作；座標文字交給既有的 `CoordsHUD`，小地圖不重複。

### 6. 每幀成本估計

| 項目 | 成本 |
|---|---|
| 地圖四邊形 | 1 次 draw、1 次貼圖取樣／像素（96×96 GUI px） |
| 玻璃外框 | 與現有 HUD 玻璃元素同級 |
| 髒區塊處理 | 只在地形變動時，硬上限 0.25 ms／幀 |
| 貼圖上傳 | 每個變動區塊 1 KB |
| 玩家移動 | **0**（只改四個頂點的 UV） |
| 實體點（僅自己的世界） | 名單每秒更新 10 次、位置每幀內插（移動和 FPS 一樣順），最多 256 個點，全部一次繪製；在伺服器上完全不跑 |

### 7. 進一步壓低成本

上面的架構已經讓每幀固定成本很小；以下是把「偶發成本」（區塊載入、方塊變動、實體）也壓到最低的做法，全部列入實作：

1. **方塊變動只重算 2 欄，不是整個區塊**：一個方塊改變只影響那一欄的顏色和它南邊那一欄的明暗，所以只重算這 2 欄、只上傳 1×2 像素。挖一格、放一格的成本從 256 欄降到 2 欄。
2. **看不到就不做事**：模組關閉時，所有掛點第一行就是一個布林判斷直接返回，並釋放貼圖；F1 隱藏、在有天花板的維度、或全螢幕畫面蓋住 HUD 時，停止處理佇列（只記錄哪些區塊變髒，便宜），回到看得見時再補。
3. **忙的時候自動讓路**：每幀預算不是固定 0.25 ms——若上一幀明顯比最近的中位數慢（例如大量區塊載入、爆炸），這一幀降到 0.1 ms；在暫停選單或載入畫面中則可放寬到 1 ms，趁玩家沒在玩時把佇列清掉。
4. **先算看得到的**：佇列依距離排序，並且地圖目前縮放下**看不到的區塊延後**，等佇列空閒時才補；縮放切換時重新排序。
5. **上傳合併與上限**：每幀最多 32 次上傳，剩下的下一幀再傳。合併做在真正會產生大量小上傳的地方——區塊載入時，南鄰區塊最北一列的重新著色原本是 16 次 1×1 上傳，改成一個 16×1 列工作、一次上傳：實測載入期間每秒上傳次數從 645–953 次降到 205–331 次。相鄰「整塊」之間的合併**沒有做**，依據是實測：單次上傳呼叫最多 0.085 ms、每秒合計 1–3 ms，而整塊是依距離順序處理、很少剛好相鄰，合併的收益在量測雜訊以下，卻要多一份暫存列緩衝與排序邏輯。
6. **零配置的資料結構**：區塊座標用 `long` 編碼，佇列與集合用遊戲內建的 fastutil（`LongArrayFIFOQueue`、`LongOpenHashSet`），不裝箱；上傳用的 `ByteBuffer` 一次配置重複使用；顏色查表 `MapColor` 64 色 × 4 種明暗預先算好。
7. **實體低頻掃描、每幀內插**：低頻的只是「名單」，不是「位置」。
   - 每秒 10 次掃描只決定**哪些實體**要畫（範圍內的有誰），結果存成一份名單。
   - **位置每一幀都即時讀**：對名單裡的每個實體，每幀用 partial tick 內插它當下的位置（`getPosition(partialTick)`），所以點的移動和遊戲 FPS 一樣順，144 / 240 FPS 就是 144 / 240 FPS 的順暢度。
   - 掃描範圍比地圖可見範圍**多 8 格**，實體走進地圖時早就在名單裡，不會晚 0.1 秒才冒出來；新加入名單的點再用約 150 ms 淡入。
   - 實體死亡或消失（`isRemoved()`）每幀檢查，當幀就移除，不等下一次掃描。
   - 所有點組成一批四邊形一次畫完。
8. **GPU 端**：不用 mipmap（避免每次上傳後重建）；4K、GUI 縮放 4 時地圖約 384×384 像素，每像素一次取樣，與一個 HUD 元素同級。

正方形與圓形的成本相同：差別只在著色器裡的距離場分支，以及「跟著朝向轉」時正方形四角需要多 √2 倍的半徑內容（貼圖本來就涵蓋整個視距，不必多算）。

## 外觀與互動

- 預設位置右上角、直徑（正方形為邊長）96 GUI px，可在 HUD 編輯畫面拖曳（實作 `HudBounds`），可調大小。
- **形狀**可選：圓形（預設）或圓角正方形。兩者的玻璃外框、玩家標記貼邊、指北「N」都跟著形狀走。
- **朝向**可選：「跟著朝向轉」（預設，自己永遠朝上）或「北方朝上」（顯示朝向光束）。
- 縮放三段：每像素 0.5 / 1 / 2 格，切換時平滑過渡（沿用 `ZoomModule` 的指數平滑寫法）。
- 位置與朝向都用 partial tick 內插，地圖平順滑動，不會一格一格跳。
- 朝向用**玩家**的朝向，不是攝影機：自由視角轉鏡頭時地圖不會亂轉。
- 顏色：原版地圖色板，可選「柔和」（往背景色混 15 %，更接近 Apple Maps 的淡色調）。
- 原有 HUD 規則照舊：F1 隱藏、開關時淡入淡出（`HudFade`）。

## 效能驗收

1. **統計開關**：`-Ds1mp1e.minimap.stats=true`，或環境變數 `S1MP1E_MINIMAP_STATS=1`（透過啟動器時用這個：啟動器會把環境變數傳給遊戲，但 JVM 參數由它決定）。每秒印一行：資料層與繪製的每幀平均／最大時間、計算與上傳呼叫各自的總時間與最大單項、上傳次數與位元組、各類工作數、視窗搬移、佇列長度。
2. **A/B 基準**：用 `Bench.java` 的 explore、chunkload、entities，小地圖開／關**交錯執行**（A, B, A, B…），條件與 `PERFORMANCE.md` 相同（4K 與 1080p 各一組）。
3. **通過條件**：平均 FPS 差距在跑與跑之間的雜訊內；1 % / 0.1 % low 不退步；>20 ms、>50 ms 幀數不增加；chunkload（大量區塊載入，最吃小地圖的情境）特別看 0.1 % low。
4. 結果記進 `PERFORMANCE.md`，沒量到的就寫 **not verified**。

## 實作階段

1. **資料層**：髒區塊佇列、每幀預算、16×16 顏色計算、環狀貼圖與小塊上傳；先用方形、不旋轉的方式畫出來確認正確。

3. **互動**：形狀與朝向選項、縮放動畫、設定、HUD 編輯器、中文。

5. **移植**：先 26.2（API 幾乎相同），再 1.21.1 等 Yarn 版本（渲染 API 不同，要改寫繪製層；資料層可共用思路）。

## 驗收結果（26.3，2026-10-23）

環境：本機（RTX 5060、驅動 591.86），**透過正式啟動器**（`itest play 26.3`，Mojang Java 25.0.1、正式啟動參數、使用者安裝的模組組合）。工具：`DevShot` 的 `S1MP1E_SHOT_MODE=minimap`（一般地形世界、種子 20261003，全自動，每張截圖前等工作佇列清空），統計開關 `S1MP1E_MINIMAP_STATS=1`。共跑 5 輪，以下是最後版本的結果。

### 實測成本（每秒統計，資料層 = 計算 + 上傳；繪製 = 這一幀小地圖其餘的 CPU 工作）

| 情境 | 資料層每幀平均 | 繪製每幀平均 | 備註 |
|---|---|---|---|
| 穩定遊玩（地形不變） | 0.0005–0.0009 ms | 0.007–0.019 ms | 每秒 0–16 次 1 像素上傳 |
| 進入世界／瞬移後大量區塊載入 | 0.03–0.21 ms | 0.01–0.07 ms | 每區塊計算約 0.07 ms；單次上傳呼叫最多 0.085 ms |

單幀上限：預算是在工作項目之間檢查，所以會超出最多一個項目。暖機後單項最多約 0.4 ms。進入世界後第一秒（JIT 尚未編譯）單幀最多 1.8 ms，只發生一次。統計中偶爾出現資料層和繪製在同一秒一起拉長（例如 1.4 ms 和 9.4 ms），但同一秒的單項工作最多只有 0.06 ms。這是整個執行緒被暫停（GC 或系統排程），不是小地圖的工作量。

### 尚未驗證

- **FPS 開／關對照**（「效能驗收」第 2、3 點）：腳本已備好（`Bench` + `S1MP1E_BENCH_MINIMAP=off|on`，1080p 與 4K 交錯）。全程約 35 分鐘，視窗必須保持在前景，因此要等使用者安排時間執行。上表的 CPU 成本是 FPS 的上界依據，但不能取代實測 FPS。
- 真人多人：只用客戶端 RemotePlayer 驗證了標記，沒有用第二台電腦開區網。
- 其他 Minecraft 版本：只有 26.3。

### 另外發現（與小地圖無關）

開發用客戶端（`gradlew runClient`：Temurin 25.0.4.1、Fabric API 0.161.0）在本機多次原生崩潰（`0xC0000005`），每次都在建立**一般地形**世界的那一刻，沒有 JVM 崩潰檔，也沒有 Windows 錯誤事件。在小地圖程式存在之前就發生過；建立平坦世界則沒有。同一台機器透過正式啟動器跑了 5 輪完整驗收，都沒有崩潰。根本原因尚未查明，查明前請用正式啟動器驗收。
